# 문제 정의서: 음성 기반 자동 페이셜 립싱크 데이터 생성

## 1. 도메인 설명

게임 개발에서 캐릭터가 대사를 말하는 장면(컷신, 대화 이벤트, NPC 대사)에는 **립싱크 애니메이션**이 필요하다.
얼굴 리그는 보통 블렌드쉐입(모프 타깃) 채널로 구성되며, 업계에서 널리 쓰이는 기준이 **Apple ARKit 52 블렌드쉐입**
(`jawOpen`, `mouthFunnel`, `mouthPucker`, `mouthPressLeft` 등)이다. MetaHuman, VRM 등 다른 규격도 이 채널과 대응시켜 쓰는 경우가 많다.

립싱크 제작 흐름은 대체로 다음과 같다.

1. 성우가 대사를 녹음한다 (.wav).
2. 애니메이터/TA가 음성을 들으며 타임라인에서 입모양 키를 찍는다 (모음 시작, 입 닫힘 등).
3. 키 사이를 다듬고, 감정 표현(눈썹, 눈, 고개)을 덧입힌다.
4. 엔진으로 내보내 확인하고 수정을 반복한다.

## 2. 현재의 문제

- **수작업 키잉 비용이 크다.** 대사 1초에 수 개의 입모양 키가 필요하고, 숙련자도 10초 대사에 수십 분이 걸린다.
- **대사량이 많다.** RPG·어드벤처 장르는 대사가 수천~수만 줄이고, 다국어 로컬라이징 시 언어마다 다시 작업해야 한다.
- **품질 편차가 생긴다.** 작업자마다 타이밍과 입모양 해석이 달라 캐릭터 간 일관성이 떨어진다.
- **기존 자동화 도구의 한계.** Rhubarb Lip Sync 등은 영어 중심이고 결과가 단순한 입모양 몇 개(A~X)라 ARKit 리그에 바로 쓰기 어렵다.
  한국어 발음(받침, 연음, 이중모음)을 고려한 도구는 드물다.

### 업무 유형: 입력과 전사

AI 도입 대상 업무를 검색 / 검사와 판독 / 분류와 배분 / 입력과 전사로 나누면, 립싱크 키잉은 **입력과 전사**에 해당한다.
"들리는 소리"를 "타임라인 위의 입모양 키"로 옮겨 적는 일이기 때문이다.

- 이 유형의 병목: **양**(대사 수천 줄 × 언어 수)과 **반복**(같은 규칙을 매번 손으로 적용). 판단보다 옮겨 적는 시간이 크다.
- 그래서 도입 근거는 "사람보다 잘한다"가 아니라 **"사람이 옮겨 적는 수준의 정확도로, 훨씬 빠르게"**다.
  성공 기준도 정확도는 사람 수준에 맞추고(6장), 시간은 크게 줄이는 형태로 잡는다.

### 이 도구를 적용하지 않을 부분

| 조건 | 해당 작업 | 이유 |
|---|---|---|
| 판정 기준이 사람마다 다른 일 | 감정 연기, 캐릭터 개성(과장, 비대칭 입모양), 컷신 연출 | 정답이 연출 의도에 따라 달라 자동화 결과를 채점할 수 없다 → 사람이 덧입히는 레이어로 남긴다 |
| 되돌릴 수 없는 일 | (해당 없음) 결과는 DCC 툴에서 수정 가능한 키 데이터라 되돌릴 수 있다 | 단, 사람이 다듬은 키를 자동 결과로 **덮어쓰는 것**은 막아야 한다 → 2차: 수정 레이어 보존 |
| 판정 기록이 없는 일 | 정답 라벨이 없는 언어/캐릭터 | 맞았는지 확인할 방법이 없다 → 이 PoC는 직접 녹음·라벨링한 데이터가 있는 한국어/영어로 한정 |

이 도구의 범위는 **"입모양 타이밍과 기본 모양"(베이스 레이어)**까지다. 연기는 사람이 맡는다.

### 주제 선정: 후보 세 개 중 립싱크를 고른 이유

| 후보 | 판단 |
|---|---|
| **음성 기반 페이셜 립싱크** | AI 출력(단어 타이밍)에서 ARKit 값까지 규칙으로 이어지고, 정답 라벨을 직접 만들 수 있다 → **선택** |
| YOLO-Pose 영상 → 관절 키프레임 | 2D 관절 좌표를 3D 회전값으로 바꾸는 준비(깊이, IK, 회전 처리, 리타게팅)가 커서 기간 안에 검증까지 어렵다. 3D 정답 데이터도 만들기 어렵다 → 다음 프로젝트로 미룸 |
| SAM 메쉬/웨이트 선택 보조 | 기존 무료 도구라는 기준선이 이미 충분하다. 2D 분할 결과를 3D 메쉬로 옮기는 문제도 있다 → 뺌 |

자세한 내용: [회고](retrospective.md) 1번

## 3. 개선 가설

> 음성 인식 모델(Whisper)로 **단어 단위 타이밍**을 얻고, 단어를 **음소 → 비짐(입모양 그룹) → ARKit 블렌드쉐입 값**으로 변환하면,
> 사람이 처음부터 키를 찍지 않아도 **바로 다듬을 수 있는 수준의 베이스 립싱크 커브**를 자동으로 만들 수 있다.

- 사람의 역할은 "처음부터 키잉"에서 "자동 결과 검수와 연기 보정"으로 바뀐다.
- 매핑 표를 설정 파일로 분리하면 리그나 캐릭터 스타일이 달라져도 코드 수정 없이 대응할 수 있다.
- 오디오 음량(RMS)을 반영하면 **한 대사 안에서** 크게 말하는 부분과 작게 말하는 부분의 입 벌림 차이를 자동으로 표현할 수 있다.
  (음량은 파일별로 정규화하므로, 통째로 속삭인 대사와 보통 대사 사이의 차이는 표현하지 못한다)

## 4. 대상 사용자

- **1차:** 게임 회사의 TA(테크니컬 아티스트), 페이셜 애니메이터. 대량의 대사에 베이스 립싱크를 빠르게 깔고 싶은 사람.
- **2차:** 인디 개발자, 버튜버/VRM 캐릭터 제작자. 전문 애니메이터 없이 대사 장면을 만들어야 하는 사람.

## 5. 입력과 출력

| 구분 | 내용 |
|---|---|
| 입력 | 대사 음성 (.wav, .m4a 등 ffmpeg로 읽을 수 있는 형식). 한국어 또는 영어 |
| AI 처리 | Whisper로 언어 감지 + 단어 타이밍 → 음소 변환 → 비짐 매핑 → 시간 배치·보간 → RMS로 세기 조절 |
| 출력 | 30fps ARKit 52 채널 키프레임 데이터 (JSON, CSV), 2D 입모양 미리보기 MP4, 채널별 커브 그래프 |

## 6. 성공 기준

만들기 전에 정량으로 적는다. 숫자의 근거는 **지금 사람이 하는 수준**이다.

| 항목 | 기준 | 숫자의 근거 (현행 수준) | 측정 방법 |
|---|---|---|---|
| 시간 단축 | 대사 1줄의 베이스 립싱크 생성 시간을 수작업 대비 **90% 이상 단축** | 수작업 라벨링 시간을 실측 (`samples/labels/manual_time.csv`). 실제 키잉은 라벨링보다 오래 걸리므로 보수적인 기준 | 자동: 파이프라인 실행 시간(모델 로드 제외) |
| 타이밍 정확도 | 모음 시작 오차 평균이 **사람끼리의 오차 이하**, 그리고 **2프레임(약 67ms) 이내**. 단, **정답 모음의 90% 이상과 짝지어진 상태에서** (재현율 ≥ 0.9) | ① 같은 파일을 시간 차를 두고 두 번 라벨링해 **사람 자신의 흔들림**을 잰다 ② 2프레임은 30fps 애니메이션에서 입모양이 소리와 어긋나 보이기 시작하는 통상적인 허용 범위 | 수작업 라벨을 정답으로 비교 (`src/evaluate.py`) |
| 입 닫힘 | ㅁ/ㅂ/ㅍ 구간 **입 닫힘 적중률 80% 이상** | 양순음은 입이 닫히지 않으면 시청자가 바로 알아채는 핵심 모양. 사람 키잉은 사실상 100%를 목표로 하므로, 자동 결과는 나머지를 사람이 고칠 수 있는 수준(5개 중 4개)으로 잡음 | 라벨된 MBP 구간(±1프레임)에서 jawOpen ≤ 0.1 이고 mouthPress ≥ 0.3인 프레임이 있으면 적중 |
| 검수 대상 선별 | 신뢰도가 낮다고 표시한 대사가 **실제 인식 오류를 놓치지 않을 것** | 사람이 모든 결과를 다시 보지 않아도 되게 하는 것이 목적 | Whisper 단어 확률 임계값 → 표시 여부와 CER 비교 |
| 재현성 | 다른 사람이 Docker 또는 Colab으로 **같은 결과** | 결과를 다른 사람이 검증할 수 있어야 함 | 같은 입력 두 번 실행 시 JSON 해시 동일 |

> 현행 수준(사람끼리의 오차, 수작업 시간)은 직접 녹음·라벨링 후 실측해서 이 표의 근거를 채운다 → `docs/evaluation.md`.

### 기준선 (지금 방식도 후보에 넣는다)

| 기준선 | 내용 |
|---|---|
| **수작업** | 사람이 음성을 들으며 키를 찍는 현행 방식. 정확도의 기준이자 시간 비교 대상 |
| **음량만으로 턱 움직이기 (AI 없음)** | 오디오 RMS를 그대로 jawOpen으로 쓰는 가장 단순한 자동화. 많은 게임이 실제로 쓰는 방식 |

음량 기준선이 Whisper 파이프라인을 이긴다면, 그것도 "AI가 필요 없다"는 결과다.

## 6-1. 입력 조건 (녹음)

판정 항목(모음 시작, 입 닫힘)이 정해지면 자료를 모으는 방식도 함께 정해진다. 모델을 바꿔도 입력 문제는 해결되지 않는다.

| 조건 | 정한 값 | 이유 |
|---|---|---|
| 녹음 환경 | 조용한 실내, 대사 앞뒤 0.5초 무음 | 잡음은 RMS 세기 조절과 단어 경계를 망가뜨린다 |
| 형식 | wav 권장 (m4a 허용), 내부에서 16kHz 모노로 통일 | Whisper 입력 규격. 원본 형식 차이를 없앰 |
| 한 파일 = 한 대사 | 파일 이름 = 대본 ID | 대본의 언어 정보와 정답 문장을 연결하기 위해 |
| 발화 스타일 | 정상 대사와 실패 사례(빠르게, 혼용, 비언어, 속삭임)를 분리 | 정상 조건의 성능과 한계 조건을 섞어 평균내지 않기 위해 |
| 라벨 | 모음은 모음 글자로, 입 닫힘은 MBP 범위로 | 채점이 이름까지 비교해야 촘촘한 한국어 모음을 정확히 짝지을 수 있음 |

## 7. 범위

- **포함:** 입 주변 채널(턱, 입술) 베이스 커브 자동 생성, 한국어·영어, 2D 미리보기.
- **제외 (다음 단계):** 눈썹·눈·고개 등 얼굴 전체 표현, Maya/Blender/UE5 임포트, 실시간 처리, 학습 기반 모델.
  (이 중 얼굴 전체 표현은 2차에서 감정 레이어로 시작했다 → [감정 레이어](emotion_layer.md))
- **알려진 위험:** 빠른 발화, 한영 혼용, 웃음·한숨 같은 비언어 소리, 속삭임에서 정확도가 떨어질 수 있다.
  이는 실패 사례(fail_01~04)로 검증하고 `docs/evaluation.md`에 기록한다.
